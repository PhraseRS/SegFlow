## 数据流图

### 场景 1: 有金字塔的文件

```
用户点击"加载底图"
    ↓
打开文件: large_image.tif (20000×20000)
    ↓
GeoUtils.read_image()
    ↓
检查金字塔: src.overviews(1) → [2, 4, 8, 16, 32] ✓
    ↓
_read_from_pyramid()
    ↓
选择层级: 20000/32 = 625 < 2048 → 使用 1/32
    ↓
读取: src.read(1, out_shape=(625, 625))
    ↓
返回: (data[625×625], profile, scale_factor=0.03125)
    ↓
UI: item.setScale(32) → 显示范围 20000×20000
    ↓
✅ 完成 (0.5秒)
```

### 场景 2: 中等文件，无金字塔

```
用户点击"加载底图"
    ↓
打开文件: medium_image.tif (8000×8000, 200MB)
    ↓
GeoUtils.read_image()
    ↓
检查金字塔: src.overviews(1) → [] ✗
    ↓
检查文件大小: 200MB < 1GB ✓
    ↓
_read_decimated()
    ↓
计算缩放: scale = 2048/8000 = 0.256
    ↓
读取: src.read(out_shape=(2048, 2048), resampling=bilinear)
    ↓
返回: (data[2048×2048], profile, scale_factor=0.256)
    ↓
UI: item.setScale(3.9) → 显示范围 8000×8000
    ↓
✅ 完成 (1-2秒)
```

### 场景 3: 超大文件，无金字塔

```
用户点击"加载底图"
    ↓
打开文件: huge_image.tif (50000×50000, 7.5GB)
    ↓
GeoUtils.read_image()
    ↓
检查金字塔: src.overviews(1) → [] ✗
    ↓
检查文件大小: 7.5GB >= 1GB ✗
    ↓
_handle_large_file()
    ↓
弹窗: "检测到超大影像，是否生成金字塔？"
    ↓
用户选择: [是] / [否]
    ↓
[是] → _build_pyramid_and_load()
    ↓
    创建 PyramidBuilder 线程
    ↓
    显示进度对话框
    ↓
    后台: build_overviews([2,4,8,16,32])
    ↓
    生成 huge_image.tif.ovr (约 2.5GB)
    ↓
    完成后重新打开文件
    ↓
    _read_from_pyramid()
    ↓
    返回: (data[1562×1562], profile, scale_factor=0.03125)
    ↓
    ✅ 完成 (首次: 5分钟, 后续: 0.5秒)

[否] → _read_decimated()
    ↓
    读取: src.read(out_shape=(2048, 2048))
    ↓
    返回: (data[2048×2048], profile, scale_factor=0.04096)
    ↓
    ⚠️ 完成 (60秒，较慢)
```

## 内存使用对比

```
原始方法 (完整加载):
┌────────────────────────────────────────────────┐
│ 20000×20000×3 bytes = 1200 MB                  │ ← OOM!
└────────────────────────────────────────────────┘

Decimated Read:
┌──────────────────┐
│ 2000×2000×3      │ = 12 MB                      ← ✓ 可行
└──────────────────┘

金字塔 (1/32):
┌────────┐
│ 625×625│×3 = 1.2 MB                             ← ⚡ 最优
└────────┘
```

## 磁盘空间使用

```
原始文件: large_image.tif
├─ 大小: 1.2 GB
└─ 内容: 20000×20000×3 RGB

生成金字塔后:
├─ large_image.tif (1.2 GB, 不变)
└─ large_image.tif.ovr (400 MB, 新增)
    ├─ Level 2: 10000×10000
    ├─ Level 4: 5000×5000
    ├─ Level 8: 2500×2500
    ├─ Level 16: 1250×1250
    └─ Level 32: 625×625

总空间: 1.6 GB (增加 33%)
```

## 性能瓶颈分析

```
完整加载流程耗时分解:

无优化 (20000×20000):
├─ 磁盘读取: 5s    ████████████████████
├─ 内存分配: 2s    ████████
├─ 数据复制: 1s    ████
└─ 缩放处理: 3s    ████████████
   总计: 11s (如果不 OOM)

Decimated Read:
├─ 磁盘读取: 6s    ████████████████████████  (GDAL 智能采样)
├─ 内存分配: 0.1s  ▌
└─ 数据复制: 0.1s  ▌
   总计: 6.2s

金字塔读取:
├─ 磁盘读取: 0.3s  █▌                        (直接读小文件)
├─ 内存分配: 0.1s  ▌
└─ 数据复制: 0.1s  ▌
   总计: 0.5s ⚡
```

## 决策矩阵

| 文件大小 | 有金字塔 | 策略 | 耗时 | 内存 |
|---------|---------|------|------|------|
| < 100MB | ✓ | 金字塔 | 0.3s | 低 |
| < 100MB | ✗ | 直接读 | 0.5s | 中 |
| 100MB-1GB | ✓ | 金字塔 | 0.4s | 低 |
| 100MB-1GB | ✗ | Decimated | 2s | 低 |
| > 1GB | ✓ | 金字塔 | 0.5s | 低 |
| > 1GB | ✗ | 询问用户 | 变化 | 低 |

## 扩展点

未来可以扩展的功能：

1. **自适应层级选择**
   - 根据当前缩放级别动态加载不同金字塔层级
   - 实现类似 Google Maps 的瓦片加载

2. **缓存管理**
   - 内存中缓存多个金字塔层级
   - LRU 策略管理缓存

3. **并行加载**
   - 多线程加载多个图层
   - 异步加载，不阻塞 UI

4. **网络支持**
   - 支持 HTTP/S3 远程 GeoTIFF
   - 利用 COG 格式的 Range Request

5. **进度反馈**
   - 详细的加载进度条
   - 预估剩余时间
